Strategic Analysis: Issues #137, #143, #151 — background_suspicion Architecture

Date: 2026-08-27
Status: ✅ Principles implemented on main (PRs #160, #161, #162)
Purpose: Document the semantic analysis and decision framework; acknowledge implementation

STATUS UPDATE: Implementation on Main

This analysis was written before discovering that PRs #160–#162 have already implemented the core architecture principles.

The following have been officially adopted on main:

1. Architecture Principles (#161)

  • docs/architecture/architecture-principles.md
  • Principle 16: Background suspicions — Possible anomalies in trusted data remain in reports but:
    • Must NOT fail CI
    • Must NOT automatically create GitHub Issues
    • Become active ONLY when explicitly selected or identity-changing operation requires them

  • Principle 4: Identity gates — New/materially changed identities require verification; automation resolves first, curator reviews only consequential unresolved questions

  • Principle 5–8: Durable knowledge vs. temporary work, external authorities as supporting tools, demand-driven lookup

2. Duplicate Classification with Authority Evidence (#160)

  • src/classical_music/authority/classifier.py
  • Classifies clusters as: confirmed_duplicate, distinct_works, catalogue_conflict, needs_authority_review
  • Returns curator_review_required: bool per cluster
  • Critical: Does NOT treat all duplicate warnings as work; distinguishes background from actionable

3. Curator-on-Demand Validation Workflow (#160)

  • reports/verification/curator-on-demand-review.md
  • Current state: 0 action required, 115 background suspicions, 74 authority clusters
  • Duplicate report: 36 Work Group clusters (21 auto-resolved, 15 background) + 38 Work clusters (9 auto-resolved, 29 background)
  • Operational: Use scripts/validate_data.py --identity-gate-id ENTITY_ID to activate entity for identity review

Validation of Initial Hypothesis

Original hypothesis: “Tooling treats background_suspicion as curator work, creating noise.”

Finding: ✅ Hypothesis was correct, but solution was already being implemented.

The analysis documents below correctly identify:

  • Bruckner versions should NOT generate curator work

  • Escalation should be demand-driven (explicit activation)

What was added on main:

Conceptual Model (Implemented on Main)

The Semantic Distinction 

Validator warns (same composer + title) → Validator finds potential duplicate
  ↓
Authority classifier examines evidence:
  - Catalogues (different WAB/opus? → background_suspicion)
  - MusicBrainz IDs (same MBID? → confirmed_duplicate; curator_review_required: true)
  - Relationships (version_of? → catalogue_conflict; curator_review_required: false)
  - Sufficiency: determines curator_review_required: bool
  ↓
If curator_review_required == false:
  → **background_suspicion** (trusted data signal)
  → Visible in report; non-blocking
  → Not curator work; does not fail CI or create Issues
  → Only actionable if explicitly activated via --identity-gate-id
  ↓
If curator_review_required == true:
  → Candidate for curator review
  → Becomes actionable ONLY if explicitly activated via --identity-gate-id
  → Then escalated to curator workflow

Original Analysis (Below) — For Reference

The following sections constitute the original conceptual analysis, which remains valid and explains the thinking behind the now-implemented principles.

ORIGINAL ANALYSIS

1. Current Situation (Pre-Implementation)

Issue #137: Bruckner Version/Concept Boundaries

Type: Curator decision already made
Status: Documented but not enforced in tooling

Decision: Bruckner symphony versions (different WAB) are intentionally separate Works.

Problem:

  • Validator generates DUP-002/003 for all pairs with identical title
  • generate_duplicate_review.py marks them auto-merge
  • No mechanism to cache this decision
  • Repeated false-positive work signals

Issue #143: Validator Warnings

Type: Architecture principle definition
Status: Defined in comments; NOT implemented

Principle (from LuHoo):

“Validator warnings in trusted legacy data are background suspicions by default”

Meaning:

  • Mere signals don’t create work
  • Only explicit activation creates curator tasks
  • Automation must exhaust all evidence first

Issue #151: Phase 2 Scope

Type: Migration/verification work
Status: Implied large scope

Reality:

  • ~80+ “duplicate” clusters are curator decisions (not merges)
  • Real work: 1 error + 5 research + 1 clarification
  • Scope would reduce ~90% once principle applied

2. The Root Problem

The tooling conflates five different things:

Signal Status Should Be Was Being Treated As
Curator decision (Bruckner) ✅ Decided Background signal Curator work
Background observation (Bach 0.91) ⏳ Unactivated Research first Curator work
Missing data (Hindemith) ⏳ Incomplete Research queue Merger queue
Data error (Stravinsky K 066) ❌ Bug Fix + prevent Duplicate candidate
Consequential decision (Prokofiev) ❓ Unresolved Curator task Mixed in with others

Result: All generate equivalent DUP-* warnings with no classification.

3. The Solution Architecture 

Validator DUP-* warning
  ↓
Authority classifier 
  → Examine evidence (catalogues, MBID, relationships)
  → Classify: confirmed_duplicate | distinct_works | catalogue_conflict | needs_authority_review
  → Assess: curator_review_required?
  ↓
If NO curator review required
  → background_suspicion
  → Visible; non-blocking; no Issue
  ↓
If YES curator review required
  → ONLY becomes work if explicitly activated
  → Use --identity-gate-id to promote to action_required

This architecture is now implemented on main.

4. Decision Table (Reference)

Scenario Classification Action Implementation
Same composer, same title, different catalogues distinct_works No action; preserve Classifier + Principle 9
Same composer, same title, same catalogue confirmed_duplicate Fix data Classifier + data review
Same composer, 0.91 title-similarity, no catalogues needs_authority_review Research phase → background Classifier + Principle 16
Same title, different opus/WAB distinct_works Preserve decision Classifier + work relationships
No expert evidence; no resolution path background_suspicion Visible; defer until activation Classifier + Principle 16

5. Impact: What Changed

Before (Pre-Main)

  • All DUP-* → Implied curator work
  • No distinction between decided/unresolved
  • Repeated warnings for curator decisions
  • Scope inflation

After (On Main)

  • DUP-* → Classified by evidence
  • Background suspicions are visible but non-blocking
  • Curator decisions are preserved, not debated again
  • Scope is demand-driven

Operational change:

# Old: 44 "duplicates" appear as curator work
python3 scripts/generate_duplicate_review.py
# → 36 WG clusters (15 manual review), 38 Work clusters (29 manual review)

# New: Same findings, different classification
python3 scripts/validate_data.py --json
# → 115 validator findings total
# → 0 action_required; 115 background_suspicion (visible, non-blocking)
# → Curator work exists ONLY if explicitly activated via --identity-gate-id
